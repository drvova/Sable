# Verifier protocol advances relevant to the Sable verifier port (LogUp-GKR, sumcheck, BaseFold/RS PCS over KoalaBear)

Context checked in the repo: Sable uses the 31-bit KoalaBear field (p = 2^31 - 2^24 + 1), a rate-1/2 RS code, BLAKE3 Merkle trees, a BaseFold opening over F_p^8, `QUERIES = 153` and `GRIND = 30` (`zk/gpcs.py` lines 50-51), an extra 11-bit grind for lookups (`GRIND_LOOKUP = 11`, `zk/llm.py` line 41), and claims 2^-103 soundness "with proven proximity bounds" (`README.md`). Proofs are 106-477 MiB; verification takes 19-56 s on one CPU core (`README.md`). A `zk/recur/` directory (`b3dom.py`, `b3ref.py`) suggests that recursion over BLAKE3 is already being explored.

Where these notes say "abstract", the claim comes from the ePrint abstract page, not from the full paper. Every work listed is on the IACR ePrint archive (eprint.iacr.org). arXiv IDs appear only where a search turned one up.

## LogUp and LogUp-GKR: the baseline and its 2024-2026 follow-ups

### Takeaway
Sable's LogUp-GKR already matches Papini & Haböck (2023/1284), and no 2024-2026 follow-up makes its verifier much cheaper. Two follow-ups matter for the port. Eagen & Haböck (2024/2067) removes the requirement that multiplicities stay below the field characteristic (relevant at p ≈ 2^31). Logup* (2025/946) changes indexed lookups, and it runs on the same fractional-GKR verifier, so a port of the GKR fractional-sumcheck verifier keeps working with both.

### Cited Findings
- **Haböck, "Multivariate lookups based on logarithmic derivatives", ePrint 2022/1530 (2022)**, https://eprint.iacr.org/2022/1530. This is the original LogUp, the baseline the user named. I did not re-fetch it in this session, so no numbers from it are cited here.
- **Papini & Haböck, "Improving logarithmic derivative lookups using GKR", ePrint 2023/1284 (received 2023-08-27; latest of 3 revisions 2025-02-20).** GKR proves the fractional sumcheck of logUp. For M ≥ 1 columns looked up in a single-column table, the prover commits to only one extra column, the multiplicities. The paper also gives a transformation from a univariate PCS to a multilinear one (proving powers of the lexicographic shift over the hypercube). The abstract gives no prover or verifier figures. — [ePrint 2023/1284](https://eprint.iacr.org/2023/1284)
- **Eagen & Haböck, "Bypassing the characteristic bound in logUp", ePrint 2024/2067 (Dec 2024, revised Feb 2025).** It removes the characteristic bound by generalizing pole multiplicity. The method also applies to the GKR variant of 2023/1284, and it unlocks fractional decomposition lookups over binary fields. It adds numerators to the fractional-sumcheck terms, which gives a weighted variant that the GKR circuit can accommodate. — [ePrint 2024/2067](https://eprint.iacr.org/2024/2067)
- **Soukhanov, "Logup*: faster, cheaper logup argument for small-table indexed lookups", ePrint 2025/946 (May 2025).** It targets indexed lookups into small tables, and the check still runs through the fractional GKR. Plonky3 has a PR that implements it on top of its existing fractional GKR. — [ePrint 2025/946 PDF](https://eprint.iacr.org/2025/946.pdf); [Plonky3 PR #2145](https://github.com/Plonky3/Plonky3/pull/2145). This description comes from search snippets; I did not read the full paper.
- **"Proofs for Deep Thought: Accumulation for large memories…", ePrint 2024/325.** It builds a batching subprotocol on LogUp-GKR for memory checking and accumulation. — [ePrint 2024/325 PDF](https://eprint.iacr.org/2024/325.pdf). Seen only as a snippet; authors not confirmed.
- **"SoK: Lookup Table Arguments", ePrint 2025/1876.** It surveys the LogUp family, including GKR+LogUp, and notes that the GKR circuit grows with the table in that setting. — [ePrint 2025/1876 PDF](https://eprint.iacr.org/2025/1876.pdf). Snippet only; authors not confirmed.
- **"GKR for Boolean Circuits with Sub-linear RAM Operations", ePrint 2025/717.** It reports a large prover speedup over LogUp on Boolean circuits with 2^30 gates, using the authors' own benchmark. This is aimed at binary circuits and is not directly relevant. — [ePrint 2025/717 PDF](https://eprint.iacr.org/2025/717.pdf)

### Inferences
- The LogUp-GKR verifier still to be ported is fixed by 2023/1284. It needs a layered GKR over (numerator, denominator) pairs, one sumcheck per layer (degree-3 round polynomials, since the layer combines eq × products of two terms), a random linear combination of the two child claims, and at the end one PCS evaluation claim for the multiplicities/columns. None of the follow-ups changes this verifier's structure, so it is the right thing to port first.
- Characteristic bound: over KoalaBear (p ≈ 2.13·10^9), a LogUp sum is sound only if the total multiplicity of any table entry stays below p. An LLM forward pass with up to 16k tokens × 64 layers can approach this for hot table entries such as zero or the common rounding entries. The README's statement that constraints "never wrap modulo p" may already cover multiplicities; check this in `zk/logup.py` and the paper. If it does not, 2024/2067 is the fix. The verifier change is small (generalized pole multiplicities and numerators in the fractional terms), but the protocol changes, so the Lisp port should follow whatever the Python prover settles on.
- Logup* would change only what the prover commits for indexed lookups. The verifier stays a fractional-GKR verifier plus one extra claim.

### Gaps
- I did not find a 2024-2026 paper that reports verifier speedups for LogUp-GKR itself, such as cross-layer batching of GKR sumchecks or fewer rounds. The verifier is already O(log² n) field operations plus PCS evaluations, so the PCS opening dominates its cost.
- No concrete prover/verifier numbers for 2022/1530 or 2023/1284 were retrieved; their abstracts give none.

## PCS / proximity testing: BaseFold and successors (WHIR, STIR, FRI-Binius, Blaze, Ligerito, list-decoding BaseFold, DEEP-FRI, proximity gaps)

### Takeaway
For fewer queries and a smaller, faster opening, WHIR (ePrint 2024/1586, EUROCRYPT 2025) is the strongest drop-in successor to BaseFold for multilinear evaluation claims. Its authors present it as a direct replacement for FRI, STIR and BaseFold. They report 63 KiB and a 360 µs verifier at degree 2^22 and 100-bit security. STIR shows that rate-shifting cuts argument size by 1.25-2.46× compared with FRI. The other key 2025-26 result points the other way. The up-to-capacity proximity-gap and mutual-correlated-agreement conjectures that "conjectured security" parameter sets rely on have been disproved (2025/2046, 2025/2010, 2026/782). Any upgrade should therefore keep to proven bounds (unique decoding or Johnson), as Sable already does. Ben-Sasson et al. 2025/2055 tightens the proven error terms in those regimes.

### Cited Findings
**Baseline**
- **Zeilberger, Chen, Fisch, "BaseFold: Efficient Field-Agnostic Polynomial Commitment Schemes from Foldable Codes", ePrint 2023/1705 (CRYPTO 2024; ePrint revised 2026-07-10).** Multilinear PCS with O(log² n) verifier cost and O(n log n) prover time. It generalizes FRI to any foldable code and is 2-3× faster than prior FRI-based multilinear PCS over the same field. With HyperPlonk compared to HyperPlonk + Brakedown, the proof is more than 10× smaller and the verifier more than 30× faster for more than 2^20 gates. Compared to HyperPlonk + FRI on ECDSA it is more than 20× faster to prove, with a verifier about 2× faster. — [ePrint 2023/1705](https://eprint.iacr.org/2023/1705)
- **Haböck, "Basefold in the List Decoding Regime", ePrint 2024/1571 (Oct 2024; revised 2025-09-04).** Proves BaseFold over RS sound for proximity parameters up to the Johnson bound 1 - √ρ. It does so through a correlated-agreement theorem for linear subcodes of RS codes, a by-product of the Guruswami-Sudan analysis. A non-linear subcode variant covers BaseFold-like protocols, including row-batched FRI-Binius and **WHIR**, in the list-decoding regime. — [ePrint 2024/1571](https://eprint.iacr.org/2024/1571)
- **Zeilberger, "Khatam: Reducing the Communication Complexity of Code-Based SNARKs", ePrint 2024/1843 (Nov 2024).** A concurrent, generic proof that BaseFold is secure in the list-decoding regime, for any linear code and field. Its own text says Haböck's bound is better for RS codes. — [ePrint 2024/1843 PDF](https://eprint.iacr.org/2024/1843.pdf)

**Successors that cut queries and proof size**
- **Arnon, Chiesa, Fenzi, Yogev, "WHIR: Reed–Solomon Proximity Testing with Super-Fast Verification", ePrint 2024/1586 (Oct 2024; EUROCRYPT 2025).** An IOP of proximity for constrained RS codes that can express multilinear (and univariate) evaluation queries, presented as a direct replacement for FRI, STIR and BaseFold. As a PCS at degree 2^22 and 100-bit security: 1.2 s to commit and open, 63 KiB communicated, 360 µs to verify. The verifier "typically runs in a few hundred microseconds", compared with several milliseconds or more for other verifiers. There is an arkworks Rust prototype at github.com/worldfnd/whir. — [ePrint 2024/1586](https://eprint.iacr.org/2024/1586); [EUROCRYPT 2025 slides](https://iacr.org/submit/files/slides/2025/eurocrypt/eurocrypt2025/174/174_slides.pdf); [worldfnd/whir](https://github.com/worldfnd/whir)
- **Arnon, Chiesa, Fenzi, Yogev, "STIR: Reed–Solomon Proximity Testing with Fewer Queries", ePrint 2024/390 (CRYPTO 2024; revised 2025-01-27).** Query complexity O(log d + λ·log log d), compared with O(λ·log d) for FRI. Each round raises the rate of the tested code. Argument size falls 1.25-2.46× compared with optimized FRI, with similar prover and verifier times. Example: 128-bit, d = 2^26, rate 1/4 gives 114 KiB, compared with 211 KiB for FRI. — [ePrint 2024/390](https://eprint.iacr.org/2024/390)
- **Diamond & Posen, "Polylogarithmic Proofs for Multilinears over Binary Towers" (FRI-Binius), ePrint 2024/504 (Mar 2024; 9 revisions to 2026-05-14; EUROCRYPT 2026).** "Ring-switching" is a sumcheck compiler that turns a large-field multilinear PCS into one over its ground field with no embedding overhead. The prover overhead is linear and the verifier overhead logarithmic. It is applied to a characteristic-2 BaseFold. — [ePrint 2024/504](https://eprint.iacr.org/2024/504). Relevance: Sable commits KoalaBear base-field data and opens over F_p^8. Ring-switching is the general way to commit small-field data and open in an extension, but the paper's instantiation is binary-tower.
- **Brehm, Chen, Fisch, Resch, Rothblum, Zeilberger, "Blaze: Fast SNARKs from Interleaved RAA Codes", ePrint 2024/1609 (EUROCRYPT 2025).** A multilinear PCS over binary fields with interleaved Repeat-Accumulate-Accumulate codes and Merkle trees. It has a linear-time prover (opening dominated by about 6n additions and 5n multiplications) and polylog verification and proof size. I did not find concrete proof-size figures. — [ePrint 2024/1609](https://eprint.iacr.org/2024/1609); [EUROCRYPT slides](https://iacr.org/submit/files/slides/2025/eurocrypt/eurocrypt2025/504/504_slides.pdf)
- **Novakovic & Angeris, "Ligerito: A Small and Concretely Fast Polynomial Commitment Scheme", ePrint 2025/1187 (June 2025).** Combines a Ligero-style matrix-vector check with partial sumcheck and works with any code whose generator rows are efficient to evaluate (RS, RM). Proof size is about log(N)²/log log(N). With 2^24 coefficients over a 32-bit binary field: a 1.3 s Julia prover on an M1 and a 255 KiB proof. A Rust crate exists. — [ePrint 2025/1187](https://eprint.iacr.org/2025/1187); [author PDF](https://angeris.github.io/papers/ligerito.pdf). Abstract-level only.

**DEEP-FRI and proximity gaps**
- **Ben-Sasson, Goldberg, Kopparty, Saraf, "DEEP-FRI", ePrint 2019/336 (2019)**, https://eprint.iacr.org/2019/336. This introduced out-of-domain ("DEEP") sampling, which WHIR and STIR reuse. Not re-fetched this session; the ID is from memory.
- **Ben-Sasson, Carmon, Ishai, Kopparty, Saraf, "Proximity Gaps for Reed-Solomon Codes" (BCIKS20), ePrint 2020/654 (FOCS 2020; J. ACM 2023)**, https://eprint.iacr.org/2020/654. It proves correlated agreement up to the Johnson bound and conjectures it up to capacity. Not re-fetched; the ID is from memory. Its J. ACM '23 citation is confirmed indirectly by 2025/2010 and 2025/2046.
- **Ben-Sasson, Carmon, Haböck, Kopparty, Saraf, "On Proximity Gaps for Reed–Solomon Codes", ePrint 2025/2055 (Nov 2025).** At unique decoding radius δ/2 it gets arbitrarily small proximity loss with O(1) exceptional z, improving on O(n). At the Johnson radius it gets zero proximity loss with O(n) exceptional z, improving on O(n²); the authors say this "substantially" lowers soundness error. At or beyond Johnson, some codes need Ω(n^1.99) exceptions. Better proximity-gap bounds imply better list-decoding bounds, so progress beyond Johnson first needs list-decoding progress. — [ePrint 2025/2055](https://eprint.iacr.org/2025/2055)
- **Crites & Stewart, "On Reed–Solomon Proximity Gaps Conjectures", ePrint 2025/2046 (Nov 2025).** Disproves the BCIKS correlated-agreement-up-to-capacity conjecture, **WHIR's mutual correlated agreement up-to-capacity conjecture**, and the DEEP-FRI list-decodability-up-to-capacity conjecture. Shows that correlated agreement with small error implies list decoding. — [ePrint 2025/2046](https://eprint.iacr.org/2025/2046)
- **Diamond & Gruen, "On the Distribution of the Distances of Random Words", ePrint 2025/2010 (Oct 2025; CRYPTO 2026).** Refutes the BCIKS capacity conjecture, with code families whose rate tends to 0 and radius to 1. The authors say "many deployed SNARKs may be less secure than previously assumed". — [ePrint 2025/2010](https://eprint.iacr.org/2025/2010)
- **Krachun, Kazanin, Haböck, "Failure of proximity gaps close to capacity", ePrint 2026/782 (Apr 2026).** A simple counterexample for RS codes over multiplicative subgroups of prime fields (Sable's setting), at distance 1 - ρ - η with η = Θ(1/log n). — [ePrint 2026/782](https://eprint.iacr.org/2026/782)
- Positive results only from search snippets (not verified): Goyal & Guruswami ePrint 2025/2054 and arXiv 2601.10047 on optimal proximity gaps for *folded* RS codes via subspace designs; arXiv 2607.08516 "Locality of Curve-Decoding and Improved Proximity Gaps"; arXiv 2607.10572 lower bounds on mutual correlated agreement error. — [arXiv 2601.10047](https://arxiv.org/pdf/2601.10047); [arXiv 2607.08516](https://arxiv.org/pdf/2607.08516); [arXiv 2607.10572](https://arxiv.org/pdf/2607.10572)

### Inferences
- **Where Sable sits now.** At rate 1/2, unique decoding (δ = 1/4) gives -log2(0.75) ≈ 0.415 bits per query, so 153 queries + 30-bit PoW ≈ 93.5 bits. The Johnson regime (δ → 1 - √(1/2) ≈ 0.293) gives ≈ 0.5 bits per query, so ≈ 76.5 + 30 ≈ 106 bits. Only the latter is consistent with the claimed 2^-103, which suggests Sable already uses Haböck's 2024/1571 Johnson-regime BaseFold analysis. This is my reconstruction; confirm it against the paper's soundness section. Because Sable relies only on proven bounds, the 2025-26 counterexamples do not affect it. They do rule out cutting queries by switching to "conjectured" up-to-capacity parameters (which would roughly halve queries at rate 1/2).
- **Best verifier and size gain: WHIR.** WHIR replaces BaseFold's single-rate folding with rounds that fold k variables, commit to the folded function on a smaller domain with a lower rate, and do out-of-domain sampling and "shift" queries. Later rounds therefore need far fewer queries. For Sable this would shrink the PCS query section (Merkle paths × 153 queries × log(n) layers) and speed up the Merkle verification that probably dominates PCS verifier time. Porting it to Lisp would need these pieces:
  - Multiple Merkle trees (one per round) and a different query schedule.
  - Out-of-domain samples absorbed into the transcript.
  - The "constrained RS" weight polynomial evaluated at the end (for multilinear evaluation claims this is an eq-polynomial product, which Sable already has for sumcheck).
  - Folding consistency checks at k-ary folding factors instead of binary.
  
  The sumcheck verifier code is reused. Use WHIR's proven parameters in the unique-decoding or Johnson regime (Haböck 2024/1571 covers WHIR at Johnson), not the conjectured MCA-up-to-capacity set disproved in 2025/2046.
- **What the queries-plus-PoW knob can still gain.** With proven Johnson bounds, each bit of PoW saves about 2 queries at rate 1/2. Moving grinding from 30 to, say, 32 bits saves only about 4 queries. Lowering the code rate (for example 1/4, with about 1 bit per query at Johnson) halves the query count but doubles commitment cost. STIR and WHIR resolve this trade-off by changing the rate per round.
- **STIR compared with WHIR.** STIR is univariate (FRI-like). WHIR natively supports multilinear evaluation claims, which is what BaseFold and the sumcheck/GKR stack produce, so WHIR is the natural successor for Sable.
- FRI-Binius, Blaze and Ligerito mostly help binary-field or prover-side settings. Ligerito's 255 KiB at 2^24 is larger than WHIR's 63 KiB at 2^22, though the field and degree differ and the setups were not matched. None of them is a clear verifier win for a 31-bit prime field.

### Gaps
- No source gave the split of Sable's 106-477 MiB proof into PCS openings and GKR/sumcheck messages. That split decides whether a WHIR swap matters for size; the 63 KiB-scale WHIR numbers suggest the PCS is not where the hundreds of MiB come from. Measure it with `zk/proofio.py`.
- WHIR's figures are for a single polynomial at 2^22 over its benchmark field. I found no WHIR benchmark over KoalaBear with F_p^8 openings and BLAKE3.
- The concrete soundness bounds in 2024/1571 and 2025/2055 (and how far 2025/2055's O(n) instead of O(n²) Johnson-radius error would cut Sable's queries) were not extracted; only abstracts were read.
- No concrete numbers for Blaze's proof size.

## Recursive verification / proof compression for hash-based systems

### Takeaway
There are two routes. (a) Classical recursion proves the verifier inside a circuit; with BLAKE3 Merkle hashing in-circuit this is costly, and outer proofs usually switch to an arithmetic-friendly hash. (b) Hash-based accumulation, ARC (ePrint 2024/1731) and WARP (ePrint 2025/753, TCC 2025), defers the expensive RS proximity checks. WARP claims a linear-time prover and a logarithmic verifier with unbounded depth in the ROM. For one-shot compression of a 100-500 MiB proof, route (a) with a WHIR or STIR outer proof is the direct path. Accumulation suits incremental, per-layer or per-token proving.

### Cited Findings
- **Bünz, Mishra, Nguyen, Wang, "Arc: Accumulation for Reed–Solomon Codes", ePrint 2024/1731 (published in Springer LNCS; venue per the Springer chapter).** A hash-based accumulation scheme for RS proximity claims, with unbounded accumulation depth, random oracles only, and claims up to the list-decoding radius. The predecessor supported only bounded depth. — [ePrint 2024/1731](https://eprint.iacr.org/2024/1731); [Springer](https://link.springer.com/chapter/10.1007/978-3-032-01907-3_5)
- **Bünz, Chiesa, Fenzi, Wang, "Linear-Time Accumulation Schemes" (WARP), ePrint 2025/753 (Apr 2025; revised 2026-06-18; TCC 2025).** "The first accumulation scheme with linear prover time and logarithmic verifier time." It is hash-based (ROM), plausibly post-quantum, supports unbounded depth, works with any linear code over a large enough field, and uses a straightline extractor through erasure correction. The abstract gives no concrete benchmarks. — [ePrint 2025/753](https://eprint.iacr.org/2025/753)
- STIR's own abstract cites the "few hundred µs" WHIR verifier and the 1.25-2.46× smaller STIR arguments as motivation for recursion: a smaller, cheaper verifier is a smaller recursive circuit. — [ePrint 2024/1586](https://eprint.iacr.org/2024/1586); [ePrint 2024/390](https://eprint.iacr.org/2024/390)

### Inferences
- In a recursive wrapper, the recursion circuit's cost is dominated by hashing: BLAKE3 Merkle paths and transcript squeezes. So the biggest lever is the number of query paths (see the PCS section), and WHIR's low query count translates directly into fewer in-circuit hashes. `zk/recur/b3dom.py` suggests BLAKE3-in-circuit is planned. If so, the Lisp verifier should keep hashing behind a clean abstraction (leaf hash, node compression, transcript permutation) so that an outer-layer hash swap (e.g. Poseidon2 over KoalaBear) is a parameter change.
- Accumulation (ARC/WARP) needs the inner proof to be built around accumulating RS proximity claims. That redesigns the protocol, not just the verifier, so it is out of scope for the current port.
- A recursive verifier is exactly the kind of circuit that can evaluate the Fiat-Shamir hash, which is the setting that KRS25-style attacks exploit (see the Fiat-Shamir section).

### Gaps
- I found no published concrete numbers, in this session, for compressing a hash-based multilinear (BaseFold/WHIR) proof of 100+ MiB into a small proof (e.g. Plonky3, Stwo or SP1 recursion benchmarks). This needs a separate search.
- Whether WARP's accumulation verifier avoids a SNARK entirely in practice was not confirmed.

## Fiat-Shamir security and transcript hygiene

### Takeaway
Bind everything: the statement, the model/weight commitment, the protocol parameters, and every prover message before each challenge, all with domain separation. Then the known practical FS attacks do not apply. Weak FS (statement not hashed) broke 36 implementations across 12 proof systems. KRS25 shows GKR+FS can be made to accept false statements for crafted circuits, for any hash. Sable proves a fixed LLM circuit that does not compute its own transcript hash, so it is outside that attack's construction. A future recursive layer would not be, and that layer needs more care. Chiesa & Orrù (ePrint 2025/536, TCC 2025) gives concrete-security bounds for duplex-sponge FS, which can justify the transcript construction.

### Cited Findings
- **Dao, Miller, Wright, Grubbs, "Weak Fiat-Shamir Attacks on Modern Proof Systems", ePrint 2023/691 (IEEE S&P 2023).** Found 36 weak-FS implementations affecting 12 proof systems. Weak FS omits the statement or public inputs from the hash, which breaks adaptive soundness. — [ePrint 2023/691](https://eprint.iacr.org/2023/691)
- **Khovratovich, Rothblum, Soukhanov, "How to Prove False Statements: Practical Attacks on Fiat-Shamir", ePrint 2025/118 (received 2025-01-25; revised 2025-12-11).** For every FS hash, some instantiation of the standard GKR-based argument is not adaptively sound: they build an explicit circuit with an accepting proof of a false statement. For any circuit C and output y, they build a functionally equivalent C* with an accepting proof that C* outputs y, so security depends on the circuit's implementation, not only on its function. Non-adaptive variants either need very large depth or rely on extra assumptions. The ePrint page lists it as a preprint. DBLP lists a CRYPTO 2025 version, which I did not confirm independently. The abstract gives no mitigations. — [ePrint 2025/118](https://eprint.iacr.org/2025/118); [Green, "How to prove false statements" Part 2](https://blog.cryptographyengineering.com/2025/02/06/how-to-prove-false-statements-part-2/)
- Matthew Green's commentary: the attack works because real hashes are publicly computable while the random-oracle model assumes they are not, so a proved program can carry a backdoor. Practical defenses are auditing the programs being proven and the heuristic "don't deploy code that does obviously suspicious things". The worst case is the flaw spreading through a recursive proof tree. — [Green, Part 1](https://blog.cryptographyengineering.com/2025/02/04/how-to-prove-false-statements-part-1/)
- **Block, Garreta, Katz, Thaler, Tiwari, Zając, "Fiat-Shamir Security of FRI and Related SNARKs", ePrint 2023/1071 (ASIACRYPT 2023).** The first formal FS-security proof for FRI and batched FRI, through round-by-round (knowledge) soundness, covering Plonk-like and ethSTARK-style protocols. A follow-up by Block & Tiwari ("On the Concrete Security of Non-interactive FRI", SCN 2024) finds deployed parameters at most about 1 bit below their targets under a stated conjecture. — [ePrint 2023/1071](https://eprint.iacr.org/2023/1071). I did not find the SCN 2024 paper's ePrint ID.
- **Chiesa & Orrù, "A Fiat-Shamir Transformation From Duplex Sponges", ePrint 2025/536 (TCC 2025).** Analyzes FS built on the duplex-sponge paradigm and gives concrete security bounds for setting parameters. It notes that indifferentiability is ill-suited to establishing knowledge soundness and ZK of the resulting argument. — [ePrint 2025/536](https://eprint.iacr.org/2025/536)

### Inferences (transcript hygiene checklist for the Lisp port)
- Absorb a protocol/domain-separation tag, all parameters (field, extension degree, rate, `QUERIES`, `GRIND`, `GRIND_LOOKUP`, number of variables), the weight commitment root, the model/config identity, and the full public statement (prompt and reply tokens) before the first challenge. This is the defense against weak FS (2023/691). Check that the Python `transcript.py` does this, and make the Lisp port byte-identical.
- Absorb every prover message before the challenge that depends on it. Sable's `transcript.py` deliberately does not absorb the final query openings ("after the last challenge (absorbing them would bind nothing…)"), which is sound only while nothing is squeezed afterwards. The port should enforce this with an assertion: no squeeze after a non-absorbed send.
- Round-by-round soundness (2023/1071) is what makes FS-compiled sumcheck/GKR/FRI sound in the ROM. Each sumcheck round polynomial must be absorbed before its challenge, and the GKR layer combination challenges must come after both child claims are absorbed.
- KRS25 needs a circuit that can, in effect, evaluate the FS hash. Sable's statement is a fixed, public LLM integer circuit F_O with no BLAKE3 evaluation, so it is not that construction. This is my reading: the fetched abstract does not state the "circuit computes the hash" condition explicitly. A recursion layer that verifies BLAKE3 transcripts in-circuit falls in the at-risk class, which argues for fixing and auditing the recursion circuit and binding its description in the transcript.
- The grinding check (30 bits PCS, 11 bits lookup) should hash the transcript state and nonce with domain separation, and the verifier must recompute rather than trust any prover-supplied digest. That is what `check_grind(base, nonce, bits)` appears to do; port it exactly.

### Gaps
- No source fetched in this session gives KRS25's own recommended mitigations verbatim; the ePrint PDF returned HTTP 403. The paper's text should be checked for its stated defenses (e.g. restrictions on circuit classes, or including the circuit description in the transcript).
- No work was found that analyzes the concrete FS security of LogUp-GKR or BaseFold specifically, the way 2023/1071 does for FRI.
